Tool Decision Matrix for Data Science on Snowflake

Five tools, five cost profiles. Choosing between them is the same decision as controlling warehouse and token spend, because credits are spent by where in the stack a question gets answered.

The stack

The rule that gives the stack its value: each layer reads only the layer directly below it. A dashboard reaching into raw because a curated column was missing is how a second, divergent definition of a metric gets born.

The five tools

SQL + visualization

Costs: SQL compute; no inference to render an existing chart.

Repeatable: exactly.

  • Reach for it when the comparison, the trend, or the uncertainty is the point
  • Aggregate in SQL, never in the client
  • Skip it for a single number — that is a sentence

Semantic layer

Costs: SQL compute, plus Analyst usage when invoked.

Repeatable: within the governed metric set.

  • Ad-hoc read-only business questions
  • Metrics, dimensions, synonyms, declared cardinality
  • Verified examples guide generation; they do not cache answers

Cortex Search

Costs: refresh, embeddings, indexed-size serving, and storage.

Repeatable: retrieval is stable, synthesis is not.

  • Passages that explain the figures, with provenance
  • Never counts, never aggregates, never a numeric answer
  • Refresh lag set to the business need, not the tightest available

AISQL functions

Costs: tokens × rows. The steepest curve in the stack.

Repeatable: yes if materialized, no if re-run.

  • Per-row classification, extraction, enrichment
  • Filter and dedupe before the model sees anything
  • Store the output. It is an expensive column, not an answer

Agent reasoning

Costs: tokens × steps × retries.

Repeatable: not by default.

  • Novel problems, debugging, root-cause questions
  • Use it once, then capture what worked as a skill
  • In production its job is orchestration, not rediscovery

Cost drivers

There is no universal product-cost ranking. Measure the same workload and quality bar before and after a change. Sources: AI Functions usage, CoCo usage, and Search costs.

The one that surprises teams A pipeline that re-classifies its whole corpus on every run has cost proportional to total data times run frequency. Incremental scoring makes it proportional to new data. Reuse requires the same input and scorer version, with failures and concurrency handled explicitly.

Decision matrix

Route by the shape of the question, not by the tool someone is excited about.

The stakeholder asksRoute to Cost driverWhy not the alternative
"What was X last quarter?" Curated metric, rendered as a chart WH only An agent re-deriving this pays tokens to reproduce a number that is already known and already agreed.
"Show me X broken out by Y" Semantic layer SQL + Analyst Hand-writing the SQL does not scale to the next twelve variants, and each variant is a chance to define X differently.
"Why did X move?" Agent reasoning, grounded on the semantic layer Tokens × steps No fixed query anticipates the cause. This is what reasoning is for.
"What are people saying about X?" Cortex Search over the text corpus Index + serve Aggregating unstructured text in SQL loses the evidence, and the evidence is the answer.
"How many of them were negative?" AISQL once, materialized, then COUNT WH on the count Retrieval has no notion of completeness. It returns the count of what it retrieved, which is a sample, and it will look like an answer.
"Classify these 400,000 rows" AISQL, incremental, filtered first Tokens × rows A per-record agent loop adds context and orchestration overhead. Compare quality and measured cost.
"Run the weekly report" Agent skill Scope + synthesis A free-form prompt drifts week to week, and the drift is invisible until someone reconciles two editions.
"Is this number right?" Deterministic gate runner; independent review when needed Compute + review Use check evidence. A second agent is not a substitute for executable assertions.
"Can you build me a dashboard for this?" Answer it once; build only if it recurs WH only Dashboards for questions asked once are the most common way DS capacity gets absorbed.

Counting with retrieval

  • Returns the count of what was retrieved
  • No notion of completeness
  • Different answer on a re-run
  • Cost scales with every question asked
  • Looks like an answer

Counting over stored labels

  • Counts the explicitly scored population
  • Reports eligible, pending, and failed coverage
  • Stable for the same snapshot and scorer version
  • Reuses persisted input/version results
  • Auditable against the gold set

Cost levers to test

Token credits

  • Reduce rows. Filter and dedupe before the model. For measurement rather than enrichment, score a sample and report an interval.
  • Reduce tokens per row. Ask for a label, not a paragraph explaining the label.
  • Reuse versioned results. Null-safe content keys, scorer version, single writer, explicit failed-output review.
  • Right-size the approach. Compare dedicated functions and alternatives at the same labeled-set quality bar.
  • Estimate first. Count each actual function input; null estimates are unknown. Output tokens are additional where billed.

Warehouse credits

  • Materialize repetition. A dashboard aggregation running per viewer is one scheduled table away from a point read.
  • Aggregate in SQL. Not in Python, not in the browser.
  • Tag SQL workloads. Include a run ID; CoCo conversation usage has separate attribution.
  • Separate the agent warehouse. Small, monitored, so exploration cannot borrow production's size.
  • Tune auto-suspend. Start at sixty seconds for intermittent standard warehouses; measure cold starts and workload needs.

Working efficiently with CoCo

Use the agent to develop and verify the method. Run settled code directly when the recurring job needs no new interpretation.

Repeatability gates

Six defects that pass every unit test, raise no error, and ship a wrong number. Each is one query. A gate returns rows only on failure.

DefectWhat it looks likeThe gate
Valid-zero from a missed join A record ranks last instead of being flagged unknown Count rows that failed to match each dimension
Fanout from undeclared cardinality Sums inflate, averages deflate, nothing errors Assert row count equals the declared grain
Double count from dual-keyed writes Every aggregate doubled, both keys look correct alone Distinct on the business tuple versus raw count
Look-ahead in a normalization Backtest accuracy improves, production does not Recompute one row at its cutoff and compare
Stale input passing a freshness check Pipeline reports healthy, inputs are frozen Assert on MAX(date), never MIN, never row count
Hindsight overwrite of a published number Accuracy history becomes unfalsifiable Predictions append-only, stamped with the live version
Gate on evidence Execute stable checks as SQL or scripts. Missing, skipped, disabled, or errored checks are not PASS. Use an independent reviewer when risk justifies the extra tokens. The analytical SQL is a starter; read the limitations in docs/07_repeatability_gates.md.

Sequencing the adoption

Do not build the whole stack before shipping anything.

1. Pick three metrics

The three that get asked about most. Not the three that are easiest.

2. Conform their sources

Curated tables with declared grain and a gate query for each.

3. Define them once

One semantic view, with the synonyms your stakeholders actually use.

4. Add verified queries

The ten questions people really ask about those three metrics.

5. Test representative questions

Use a bounded set of questions and paraphrases with reviewed expected results.

6. Widen

After quality and cost criteria pass. Repeated agreement alone does not prove correctness.

The metric to report upward CoCo credits per accepted task; scoring credits per 1,000 validated records, with quality and coverage alongside. A usage-history row is not an answer. The measured exercise tests first run, unchanged rerun, changed input, and changed scorer. No savings are assumed.
